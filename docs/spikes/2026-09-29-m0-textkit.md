# Milestone 0: TextKit 1 vs TextKit 2

Run on 2026-09-30 on a Mac16,12 (Apple M4) with macOS 27.0 (26A428) and Xcode 27.0 (27A266a). Spike branch `spike/m0-textkit` at commit `6ffb924` (local only; not pushed). Plan: [`docs/superpowers/plans/2026-09-29-m0-textkit-spike.md`](../superpowers/plans/2026-09-29-m0-textkit-spike.md).

The manual checks were driven by an agent with synthetic key and mouse events and judged from screenshots, in dark mode. Where that cannot judge something (flicker while scrolling, what VoiceOver actually says), the result is marked provisional and needs a check by hand.

## Result

**TextKit 1**, by the plan's decision rule, pending acceptance. Neither engine has a blocker. TextKit 1 has no stability problem: revisiting a scroll offset shows the same text (`scrollDriftChars` 0) and text above a growing table does not move. TextKit 2 re-estimates document heights while scrolling (134 height changes) and lands on different text when an offset is revisited (`scrollDriftChars` 248,886), which is exactly the scroll-jump risk the design's stability principle guards against. Both engines miss the 8 ms restyle budget by about 7 ms, and the cost is the shared controller's, not the engine's. TextKit 2 renders the islands more cleanly (no fence gaps, no grid offset) and opens faster, so the choice is close and hinges on scroll stability.

## What surprised us

- **Null-glyphed newlines do not break lines in TextKit 1.** Nulling every table character, including its inner line breaks, merged the whole table into one 18 pt line fragment, which ignored the reserved minimum line height, so the grid overlapped the text below. Keeping the line-break control glyphs fixed it.
- **Restyling dropped fallback fonts.** Resetting fonts in `didProcessEditing` runs after NSTextStorage picks fallback fonts, so 日本語 and emoji vanished on both engines until styling ends with `fixAttributes(in:)`.
- **TextKit 1 grid positioning is off by one line until the first edit**, and TextKit 1 logs `invalid glyph index` warnings (16 on the big fixture). An `ensureLayout` call to settle the mapping did not help and made the benchmark hang in 2 of 4 runs, so it was removed.
- **TextKit 2 kept keyboard focus in the grid** across attachment-view rebuilds, which the plan expected to be fragile.
- **TextKit 2 drew no background for code blocks**, and scrolled 4× slower per step, though well inside 16 ms.
- **Neither engine gives VoiceOver the grid.** Both expose the raw source, markers included.
- **The spike's table serializer drops column alignment** (`:--` becomes `---`), which the design's Milestone 2 serializer must not.

## Consequences for Milestone 1

- Build the editor on TextKit 1 with null glyphs for markers; keep table line breaks as control glyphs and collapse the extra lines with paragraph styles.
- Fix grid placement: take the reserved line's rectangle from the layout manager after layout completes, and understand the `invalid glyph index` warnings before relying on glyph queries.
- Keep the caret out of hidden island source (Review Focus 5): move ↑/↓ and clicks around a table onto the grid, and block typing in hidden ranges.
- Reparse from the edited block: the full reparse plus restyle costs about 15 ms p95, twice the budget. The spike's island extraction is quadratic in tables × spans and is a first suspect.
- Expose the grid to accessibility, and speak rendered text rather than markers, before claiming VoiceOver support.
- Revisit TextKit 2 if a future macOS stops re-estimating heights while scrolling, since it handled islands more cleanly.
